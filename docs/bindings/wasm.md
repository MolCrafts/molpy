# WASM Quickstart

The npm package `@molcrafts/molwasm` exports the classes and functions generated
by `wasm-bindgen`. It is built for bundlers (Vite, webpack, Rollup with a
WebAssembly plugin): importing the package loads and starts the WebAssembly
module, so there is no separate initialization call.

## 1. Install and Import

```bash
npm install @molcrafts/molwasm
```

```ts
import { SmilesIr, Conformer, writeXyz } from "@molcrafts/molwasm";
```

Configure your bundler to load `.wasm` modules. A custom build with
`wasm-pack build --target web` instead exports an async default `init()`
that must be awaited before any other call.

## 2. Parse, Embed, and Export

```ts
const ir = SmilesIr.parse("CCO");
const frame2d = ir.toFrame();
const frame3d = new Conformer("fast", true, 42).generate(frame2d);

console.log(writeXyz(frame3d));
```

The API shape mirrors Rust and Python, with JavaScript naming conventions:
`SmilesIr::parse` becomes `SmilesIr.parse`, `to_frame` becomes `toFrame`,
`Conformer(...).generate` stays `Conformer.generate`, and the Rust door
`molrs::io::write_xyz` (Python `mp.io.write_xyz`) becomes `writeXyz` —
every class and function is named after its molrs owner, and every door names
its format. There is one door per format and direction: `read<Fmt>(source)`
takes a `string` (always the text of a file) or a `Uint8Array` (its bytes;
the binary DCD, TRR and XTC take bytes only), and `write<Fmt>(frame)` returns
the file (a `string` for a text format, a `Uint8Array` for a binary one).
There are no `Str` / `Bytes` twins. A format molrs reads with
functions only (XSF, cube, CHGCAR, AMBER inpcrd / `.ac`) has no reader class
here either. The TypeScript declarations in the package (`molwasm.d.ts`) are
the source of truth for exported names.

```ts
import { readXyz, writePdb } from "@molcrafts/molwasm";

const frame = readXyz(await file.text());                         // text
const same = readXyz(new Uint8Array(await file.arrayBuffer()));   // bytes
const pdb = writePdb(frame);
```

## 3. Inspect Columns

Frames contain blocks, and blocks contain typed columns. A column reads back
as the typed array of its stored dtype — `Float64Array` for floats — and no
method names a dtype. `dtype(key)` reports molrs core's dtype name (`"float"`,
`"int"`, `"uint"`, `"string"`, …), the one Python and the Frame schema use:

```ts
const atoms = frame3d.get("atoms"); // throws if absent; check with frame3d.has("atoms")

const x = atoms.copy("x");          // owned Float64Array
const y = atoms.copy("y");
const z = atoms.copy("z");

console.log(atoms.nRows, atoms.dtype("x"), x[0], y[0], z[0]);
```

`copy` returns an owned typed array that is safe to keep. `view(key)` returns
a zero-copy view into WebAssembly memory instead; it is faster for large
columns but becomes invalid when the module's memory grows, so read it
immediately or prefer `copy` until profiling says otherwise. `set(key, array)`
writes a column and takes its dtype from the typed array's constructor
(`Float32Array` and plain `number[]` are refused). The
[package README](https://github.com/MolCrafts/molrs/tree/master/molwasm#core-data-model-molrscore)
has the full dtype table.

## 4. Read Record Files

The browser reads the same `*.mrec` [record files](../user-guide/15_records.md) that
Python and Rust write. A packed `*.mrec.zip` arrives as bytes:

```ts
import { MrecFile, MrecReader } from "@molcrafts/molwasm";

const bytes = new Uint8Array(await (await fetch("run.mrec.zip")).arrayBuffer());
const reader = new MrecReader(bytes);
const first = reader.readFrame(0);
console.log(reader.nFrames(), first?.get("atoms").nRows);

const file = new MrecFile(
  new Uint8Array(await (await fetch("water.mrec.zip")).arrayBuffer()),
);
console.log(file.sections());
const snapshot = file.frame();
```

`MrecFile` reads a record one section at a time (`sections()`, `frame()`,
`system()`, `meta()`) and `MrecReader` decodes one trajectory frame per call.
Both take the packed bytes, a `Map<path, Uint8Array>` of the record's files,
or a storage host that serves chunks on demand through callbacks, so a large
trajectory never has to be downloaded whole.

## 5. Build from Source

The npm publish pipeline uses this bundler target:

```bash
cd molwasm
wasm-pack build --release --target bundler --scope molcrafts --out-name molwasm
```

This writes `molwasm/pkg/`. That directory is generated and ignored by git.
Applications can link it locally during development:

```json
{
  "dependencies": {
    "@molcrafts/molwasm": "link:../molwasm/pkg"
  }
}
```

## 6. Variant Builds

The default npm build includes SMILES, I/O, compute, conformer, Voronoi,
builder, and stream support. Smaller local builds can disable default Cargo
features, but a page should load only one variant of the package at a time
because each WebAssembly module owns a distinct JavaScript class identity.


## Reference

`@molcrafts/molwasm` ships its TypeScript declarations in the package itself:
`molwasm.d.ts`, generated by `wasm-bindgen` from the Rust doc comments of the
`molwasm` crate. Editors and `tsc` pick them up from the installed package,
so hover documentation and signatures match the version you installed.

To read them from a source checkout, build the package with the same flags as
release publishing and open `molwasm/pkg/molwasm.d.ts`:

```bash
cd molwasm
wasm-pack build --release --target bundler --scope molcrafts --out-name molwasm
```

The generated `pkg/` directory is not committed.

## Main exports

| Area | Exports |
| --- | --- |
| Core data model (`molrs::core`) | `Frame` (`getMeta` / `setMeta` / `metaKeys`, `delBlock`), `Block` (`get`, `view`, `copy`, `set`, `dtype`, `shape`, `nRows`), `Box` (`new Box(cell, origin, pbc)` with `Cell.matrix` / `lengths` / `lengthsAngles` / `lengthsTilts` / `undefined()`, `Box.bounding(points, padding, pbc)`; `toFrac`, `toCart`, `delta`, `wrap` → `{xyz, shifts}`, `corners`, …), `NDArray`, `Topology` (`fromFrame`, `delAtom` / `delAtoms` / `delBond` / `delBonds`), `TriMesh`, regions (`Sphere`, `Cuboid`, `Parallelepiped.create(cell, origin)`, …, `Region`), `NeighborList` / `NeighborQuery` / `Neighbors`, `covalentRadius` |
| SMILES and 3D | `SmilesIr.parse(text)` (`toFrame`), `SmilesIr.fromFrame(frame).toString()`, `CgSmilesIr.parse(text)` (`toFrame`), `Conformer` (`generate`) |
| File formats | one door per format and direction, the camelCase of Rust's and Python's `read_<fmt>` / `write_<fmt>`: `readX(source: string \| Uint8Array)` (a string is always the text of a file) and `writeX(frame)` — `readPdb` / `writePdb`, `readXyz` / `writeXyz`, `readSdf`, `readGro` / `writeGro`, `readMol2` / `writeMol2`, `readCif` / `writeCif`, `readXsf` / `writeXsf`, `readCube` / `writeCube`, `readPoscar` / `writePoscar`, `readChgcar`, `readInpcrd`, `readAc`, `readPrmtop`, `readLammpsData` / `writeLammpsData`, `readLammpsDump` / `writeLammpsDump`, and the binary `readDcd` / `writeDcd`, `readTrr` / `writeTrr`, `readXtc` / `writeXtc` (`Uint8Array` only); `readCsvBlock` / `writeCsvBlock` (a `Block`); the reader classes `CifReader`, `GroReader`, `Mol2Reader`, `VaspPoscarReader`; `readStl` → `TriMesh`; `readLammpsLog` → `LammpsLog`, `isLammpsLog`; wire-encoded frames: `readWireFrame(source, FrameEncoding)` / `writeWireFrame(frame, FrameEncoding)` |
| Chunk-fed streams (the one reader of their format) | `XyzStream`, `PdbStream`, `SdfStream`, `LammpsDataStream`, `LammpsDumpStream`, `DcdStream`, `XtcStream`, `TrrStream` (`FrameOffset`) |
| Record files (`*.mrec`) | `new MrecFile(source)` (`sections()`, `frame()`, `system()`, `meta()`), `new MrecReader(source)` (`readFrame`, `readColumns`, …), each over packed bytes, a file map or a storage host |
| Perception | `assignRings`, `assignAromaticity`, `assignKekuleBondOrders` (mutate the frame they are given), `addHydrogens`, `removeHydrogens` (return a new frame) |
| Analysis (`molrs::compute`) | `Rdf`, `Msd`, `Cluster`, `Vacf`, `Steinhardt`, `PmftXy`, `DistributionFunction`, … (one class per molrs compute type, under its Rust name; `Msd` / `Vacf` take per-frame records `{a, dt, simbox?}`); `molrsComputeCatalog()` lists them all |
| Force fields | `UffTypifier`, `Mmff94Typifier`, `Mmff94sTypifier` (`typify`, `forcefield` → `ForceField`), `PotentialCompiler` (`compile` → `Potentials`), `Potentials` (`evaluate`), `Lbfgs` (pairs from a `NeighborList`'s `Neighbors`), `KineticEnergy` (`new KineticEnergy(units, mvv2e?, boltzmann?)`), `CarbonTubeBuilder` (`setExtent(TubeExtent.cells(n) \| TubeExtent.length(l))`) |
| Schema | `schemaDocument`, `keysDocument`, `schemaColumnDtype` |

The [package README](https://github.com/MolCrafts/molrs/tree/master/molwasm#readme)
shows each of these in use, including the column dtype table and the record
readers.
