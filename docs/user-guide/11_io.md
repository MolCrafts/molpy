# I/O: Reading and Writing File Formats

Readers turn files into explicit format products; writers consume `Frame`s plus any format-owned side inputs. To add support for a **new** format, see [Developer Guide: I/O Formats](../developer/extending-io.md).

MolPy's I/O covers three kinds of file: **data** (single-frame structures), **trajectory** (multi-frame sequences), and **forcefield** (parameter files). All three are `mp.io`. A one-frame structure door is a function at its top named after its format — `read_<fmt>` / `write_<fmt>` — and everything else is a class in that format's submodule (`mp.io.smiles`, `mp.io.cgsmiles`, `mp.io.lammps`, `mp.io.mrec`, `mp.io.pdb`, `mp.io.xyz`, `mp.io.gromacs`, `mp.io.openmm_xml`, `mp.io.amber`, …): a `<Fmt>Reader` / `<Fmt>Writer` for every frame of a multi-frame file, a `…ForcefieldReader` / `…ForcefieldWriter` for a force field. No door picks the format from a file name: you call the format's own.

A reader takes a `pathlib.Path`, `bytes`, or `mp.io.Text(s)` for a file's text held in memory; a plain `str` is refused, because it could name a file or hold one. A writer takes a `pathlib.Path`, or a `bytearray` that receives the bytes.

## Data files

Every data reader returns a `Frame`: blocks, dict-like `meta`, and an optional `box`. What a format holds beyond the structure is frame meta — a LAMMPS data file's `* Coeffs` text, header counts and Type Labels included.

### Reading

Every format has its own reader function on `mp.io`:

The examples below share this setup:

```python
from pathlib import Path

import molpy as mp

frame = mp.Frame(
    blocks={
        "atoms": {
            # A writer asks for the columns its format has fields for: LAMMPS
            # wants `type` labels, `mol_id` and `mass`, XSF wants `atomic_number`.
            "id": [1, 2, 3, 4, 5, 6],
            "mol_id": [1, 1, 1, 2, 2, 2],
            "type": ["OW", "HW", "HW", "OW", "HW", "HW"],
            "element": ["O", "H", "H", "O", "H", "H"],
            "atomic_number": [8, 1, 1, 8, 1, 1],
            "mass": [15.999, 1.008, 1.008, 15.999, 1.008, 1.008],
            "charge": [-0.834, 0.417, 0.417, -0.834, 0.417, 0.417],
            "x": [1.0, 1.96, 0.76, 6.0, 6.96, 5.76],
            "y": [1.0, 1.0, 1.93, 6.0, 6.0, 6.93],
            "z": [1.0, 1.0, 1.0, 6.0, 6.0, 6.0],
        }
    }
)
frame.box = mp.Box(mp.core.Cell.lengths([20.0] * 3))
```

```python
# docs: skip — reads offline structure files; I/O unit-tested with fixtures
import molpy as mp

frame = mp.io.read_pdb(Path("molecule.pdb"))
frame = mp.io.read_gro(Path("system.gro"))
frame = mp.io.read_mol2(Path("ligand.mol2"))
frame = mp.io.read_lammps_data(Path("system.data"), atom_style="full")
frame = mp.io.read_xyz(Path("coords.xyz"))
frame = mp.io.read_cif(Path("crystal.cif"))
frame = mp.io.read_xyz(mp.io.Text("1\n\nO 0 0 0\n"))  # a file's text in memory
```

A CIF's symmetry stays with the frame: `read_cif` keeps the operator loop
verbatim in `frame.meta["symops"]` and the Hermann–Mauguin symbol in
`frame.meta["space_group"]`, each only when the file states it. The atoms
block is the asymmetric unit as written; `mp.builder.Lattice.from_cif(frame)`
expands it into the full cell (see
[Nanostructures](04_nanostructures.md#bulk-crystals-from-a-cif)).

SMILES text in and out is `mp.io.smiles` (`read_smiles` / `write_smiles`); a local SMARTS out is a `perceive` pattern, whose `str` is the SMARTS text:

```python
mol = mp.io.smiles.read_smiles("CCO").to_atomistic()
pattern = mp.perceive.SmartsPattern.from_environment(mol, mol.atoms[0])
print(str(pattern))  # the SMARTS text
print(mp.io.smiles.write_smiles(mol))  # and SMILES back out
```

Readers take a path and return a `Frame`. A LAMMPS data file's force field is
its `* Coeffs` sections, which the structure reader keeps as text in
`frame.meta["lammps_coeffs_text"]`;
`mp.io.lammps.LammpsForcefieldReader().read_data_coeffs(frame)` reads them from
that frame — the file is read once — into a `ForceField` when you want them. Each row is named by the
file's Type Labels, and the units are the file's own (its `write_data` title
line), else `"real"` — pass `units=` for a file that does not state them:

```python
# docs: skip — reads an offline data file; I/O unit-tested with fixtures
frame = mp.io.read_lammps_data(Path("system.data"))
ff = mp.io.lammps.LammpsForcefieldReader().read_data_coeffs(frame)
print(frame.meta["lammps_counts"])  # atoms=…,bonds=…,atom_types=…
```

The `Frame` returned by a data reader typically contains an `"atoms"` block with coordinates, and may contain `"bonds"`, `"angles"`, and `"dihedrals"` blocks depending on the format.

```python
# docs: skip — reads offline structure files; I/O unit-tested with fixtures
frame = mp.io.read_pdb(Path("water.pdb"))
print(frame["atoms"].n_rows) # number of atoms
print(list(frame["atoms"].keys())) # ['x', 'y', 'z', 'id', 'element', 'name', ...]
```

### Writing

Writers follow the same one-door-per-format pattern:

```python
mp.io.write_pdb(Path("output.pdb"), frame)
mp.io.write_gro(Path("output.gro"), frame)
mp.io.write_lammps_data(Path("output.data"), frame)
mp.io.write_xsf(Path("output.xsf"), frame)

buffer = bytearray()
mp.io.write_xyz(buffer, frame)  # the file's bytes, in memory
```

For LAMMPS, the most common pattern writes the data file and the force-field
coefficients side by side: `write_lammps_data` for topology + coordinates, and
`mp.io.lammps.LammpsForcefieldWriter(frame).write(path, forcefield)` for the
coefficients. The coefficient writer is built on the frame: every type label of the frame is looked
up in the force field by its exact name, and only the coefficients the frame
uses are written. The pair cutoff is a run setting you declare on the pair
style; molpy never invents one.

```python
ff = mp.ff.forcefield.ForceField(name="demo", units="real")
# The 1-2 / 1-3 / 1-4 pair weights (LJ, then Coulomb) are stated, never assumed.
ff.set_special_bonds([0.0, 0.0, 0.5], [0.0, 0.0, 0.8333])
atom_style = ff.def_style("atom", "full")
ow = atom_style.def_type("OW", mass=15.999, charge=-0.834)
hw = atom_style.def_type("HW", mass=1.008, charge=0.417)
pair_style = ff.def_style("pair", "lj/cut")
pair_style.def_type("OW", ow, epsilon=0.1521, sigma=3.1507)
pair_style.def_type("HW", hw, epsilon=0.0, sigma=0.0)
pair_style["cutoff"] = 10.0
ff.def_style("pair", "coul/cut")["cutoff"] = 10.0  # the charges' pair term

mp.io.write_lammps_data(Path("system.data"), frame)  # topology + coordinates
mp.io.lammps.LammpsForcefieldWriter(frame).write(Path("system.ff"), ff)  # force-field coefficients
```

### Supported data formats

| Format | Read | Write | Notes |
|--------|------|-------|-------|
| PDB | `read_pdb` | `write_pdb` | ATOM/HETATM + CRYST1 + CONECT |
| GRO | `read_gro` | `write_gro` | GROMACS structure |
| MOL2 | `read_mol2` | `write_mol2` | Tripos MOL2 |
| LAMMPS data | `read_lammps_data` | `write_lammps_data` | `atom_style` fixes the `Atoms` layout (detected when `None`); `* Coeffs` kept as text in `meta["lammps_coeffs_text"]`; `type_labels={"atoms": [...]}` declares unused labels; a Drude system gets its `fix drude` flags |
| LAMMPS molecule | `read_lammps_molecule` | `write_lammps_molecule` | Template files |
| XYZ | `read_xyz` | `write_xyz` | Extended XYZ; an n-wide property is one `(N, n)` column |
| XSF | `read_xsf` | `write_xsf` | XCrySDen format |
| AMBER AC | `read_ac` | — | Antechamber format; emits `charge` |
| AMBER inpcrd | `read_inpcrd` | — | AMBER coordinates; `frame=` reads them into an existing frame |
| AMBER prmtop | `read_prmtop` | — | Structure; `mp.io.amber.AmberPrmtopForcefieldReader().read_system(path)` returns `(ForceField, Frame)` |
| CIF | `read_cif` | `write_cif` | Crystallographic Information File |
| VASP POSCAR | `read_poscar` | `write_poscar` | VASP structure |

LAMMPS `fix bond/react` systems are written by
`mp.io.write_lammps_bond_react_system(workdir, frame, ff, templates)` (data,
`.ff`, `_pre.mol` / `_post.mol` and `.map` files with one type numbering),
from `mp.io.lammps.BondReactTemplate(pre, post, initiator_atoms, ...)`.

## Trajectory files: lazy Frame sequences

A trajectory reader is a lazy, indexed, iterable sequence of frames: random access indexes the file once and then seeks, and iteration walks it in order, so a large trajectory is never held in memory whole.

### Reading

```python
with mp.io.lammps.LammpsDumpWriter(Path("dump.lammpstrj")) as writer:
    for snapshot in [frame, frame, frame]:
        writer.write(snapshot)
reader = mp.io.lammps.LammpsDumpReader(Path("dump.lammpstrj"))

print(len(reader)) # total frame count: 3
frame_0 = reader[0] # random access by index
frame_last = reader[-1] # negative indexing
subset = reader[0:2] # slicing returns list[Frame]
```

Iteration is lazy — frames are parsed on demand, one at a time:

```python
for snapshot in reader:
 atoms = snapshot["atoms"]
 # process one frame at a time
```

Always close the reader when done (or use it as a context manager) to release the file:

```python
reader.close()
```

### Writing

A trajectory writer is opened once and takes one frame per `write`:

```python
frames = [frame, frame]
with mp.io.lammps.LammpsDumpWriter(Path("output.lammpstrj")) as writer:
    for snapshot in frames:
        writer.write(snapshot)
with mp.io.xyz.XyzWriter(Path("output.xyz")) as writer:
    for snapshot in frames:
        writer.write(snapshot)
```

### mrec: scientific records

An `*.mrec` record is a Zarr-v3 **directory** (not a single file) that holds a
trajectory, self-describing. Frames may be **ragged** — a growth or
packing run whose atom count changes per frame stays one trajectory — and the
record carries `step` labels and, optionally, per-frame blocks such as `bonds`.

For a run too large to hold in memory — or one that **grows a frame at a
time** — write it append-first instead of building the whole `Trajectory`.
The schema comes from prototype frames:

```python
frames = []
for step in range(5):
    snapshot = frame.copy()
    snapshot["atoms"]["x"] = snapshot["atoms"]["x"] + 0.1 * step  # a toy drift
    frames.append(snapshot)

schema = mp.io.mrec.SequenceSchema.from_frames(frames[:1])
with mp.io.mrec.MrecWriter(Path("run.mrec"), schema) as writer:
    for step, snapshot in enumerate(frames):
        writer.append(snapshot, step=100 * step)  # time=... is optional
# frames land on close; call writer.flush() to land them sooner
```

Read it back lazily with the one-frame cursor, under `mp.io.mrec`:

```python
reader = mp.io.mrec.MrecReader(Path("run.mrec"))
print(len(reader))             # 5 — committed frame count, index only, no decode
print(reader.step)             # [0, 100, 200, 300, 400] — per-frame step labels
last = reader[-1]              # random access; negative indexing
if reader.has_block("bonds"):  # decide once, not per frame
    ...
for snapshot in reader:        # lazy iteration, one decode at a time
    ...
```

The schema is pinned at create: every appended frame is checked against it. To
record a section that only appears partway through a run — per-frame `bonds` in
a growth run — declare it up front by including a frame that carries an
even-empty `bonds` block in the schema prototype. A small record that fits in
memory is written in one call, `mp.io.write_mrec(path, trajectory=...)`, and
`reader.to_trajectory()` reads every frame back as an `mp.Trajectory`. A record
holding one snapshot is written with `mp.io.write_mrec(path, frame=...)` and read
with `mp.io.mrec.MrecFile(path).frame()`, a topology-only record with `system=` /
`MrecFile(path).system()`, and `MrecFile(path).sections()` says which of these a
record holds.

A force field travels in the same record as its own `forcefield` section, with
its units declared and never converted:

```python
mp.io.write_mrec(Path("water.mrec"), frame=frame, forcefield=ff)
section = mp.io.mrec.MrecFile(Path("water.mrec")).forcefield()  # an mp.io.mrec.ForceFieldSection, None when absent
ff_back = section.to_forcefield()
```

`frame.meta` is stored typed (an `i32` stays `i32`, NaN stays NaN).

A float column can declare a **precision** — an absolute tolerance in the
column's units. The writer rounds the values to that grid and compresses the
column, which cuts coordinates to a few bytes per atom per frame; the reader
hands back the rounded values and the declaration. Without a declaration the
floats are stored exactly.

```python
snapshot = frame.copy()
snapshot["atoms"].set_precision("x", 1e-3)  # keep x to a thousandth of an Å
mp.io.write_mrec(Path("snapshot.mrec"), frame=snapshot)
record = mp.io.mrec.MrecFile(Path("snapshot.mrec"))
back = record.frame()
print(back["atoms"].precision("x"))  # 0.001
print(record.sections())  # ['frame', 'meta']
```

A trajectory takes each column's precision from its prototype frame
(`SequenceSchema.from_frames`), or from `schema.declare_precision(block,
column, precision)`.

### Supported trajectory formats

| Format | Read | Write | Notes |
|--------|------|-------|-------|
| LAMMPS dump | `lammps.LammpsDumpReader` | `lammps.LammpsDumpWriter` | Custom columns supported (`set_columns`) |
| XYZ | `xyz.XyzReader` | `xyz.XyzWriter` | Multi-frame XYZ |
| PDB | `pdb.PdbReader` | `pdb.PdbWriter` | One `MODEL` per frame |
| GRO | `gro.GroReader` | `gro.GroWriter` | Multi-frame GRO |
| DCD | `dcd.DcdReader` | `dcd.DcdWriter` | NAMD/CHARMM binary |
| TRR | `trr.TrrReader` | `trr.TrrWriter` | GROMACS full precision |
| XTC | `xtc.XtcReader` | `xtc.XtcWriter` | GROMACS compressed |
| mrec record | `mrec.MrecReader` | `mrec.MrecWriter` / `write_mrec(path, trajectory=...)` | Zarr-v3 directory; ragged; `step` labels; per-frame blocks |

Names come in pairs: `mp.io.read_X` / `mp.io.write_X` for one frame (a reader
returns the file's first frame), and the format's own lazy reader and writer
classes for a sequence of frames (`mp.io.lammps.LammpsDumpReader`,
`mp.io.xyz.XyzReader`, `mp.io.pdb.PdbReader`, `mp.io.gro.GroReader`,
`mp.io.dcd.DcdReader`, `mp.io.trr.TrrReader`, `mp.io.xtc.XtcReader`, and their
`…Writer`s); `list(reader)` gives a `list` of frames.

One-frame doors are ``mp.io.read_*`` / ``mp.io.write_*``; an mrec record is
written with ``mp.io.write_mrec`` or ``mp.io.mrec.MrecWriter`` and read with
``mp.io.mrec.MrecFile`` or ``mp.io.mrec.MrecReader``.

## Log files: simulation run metadata

LAMMPS log files are different from data and trajectory files: they describe what LAMMPS did during each `run`, not where atoms were. The parser keeps that structure: a `LammpsLog` holds the header, one `LammpsRun` per `run`, and the raw text of anything not represented by a dedicated field.

The key idea is: **use `read_lammps_log` when you need run-level diagnostics such as thermo output, loop timing, load balance, neighbor statistics, or warnings.** A run's `thermo` is a table you index by the LAMMPS column name, so downstream analysis can use dynamic column names directly.

In practice, each run is accessed in the same order it appears in the log:

```python
# docs: skip — reads offline log.lammps; I/O unit-tested with fixtures
log = mp.io.read_lammps_log(Path("log.lammps"))
run = log.runs[0]

print(run.thermo.columns)             # ["Step", "Temp", ...]
print(run.thermo["Temp"].mean())      # one float64 column
print(run.thermo.rows.shape)          # (n_rows, n_columns)
print(run.loop_time.seconds)
print(run.neighbor_statistics.dangerous_builds)
```

`read_lammps_log(mp.io.Text(text))` parses an in-memory string the same way, and
`log.to_dict()` gives the nested JSON-friendly form.

### Supported log formats

| Format | Read | Write | Notes |
|--------|------|-------|-------|
| LAMMPS log | `read_lammps_log` (`mp.io.Text(text)` for in-memory text) | — | `mp.io.lammps.LammpsLog` → `LammpsRun` → `LammpsThermo`, parsed natively |

## Force field files: ForceField in, ForceField out

Force field readers parse parameter files into `ForceField` objects. Force field writers serialize `ForceField` objects into engine-specific formats.

LAMMPS `*.ff` includes are **read and written**
(the LAMMPS force-field reader/writer). Molpy's
`mp.io.lammps.LammpsForcefieldReader().read(source)` and
`mp.io.lammps.LammpsForcefieldWriter(frame).write(sink, ff)` are the public API;
pass `mp.io.Text(text)` / a `bytearray` for text in memory. The force-field IR adopts the LAMMPS standard
(every style's expression, factors and parameter units are its LAMMPS
style's; angle values in degrees), so a coefficient is read and written as it
stands (`K = k`). The reader declares the file's `units` on the force field
and converts nothing; the writer converts energies and lengths only when the
target `units` differs from the force field's.

### Reading

```python
# docs: skip — reads offline force-field files; I/O unit-tested with fixtures
ff = mp.io.openmm_xml.OpenmmXmlReader().read(mp.resources.get_path("forcefield/tip3p.xml"))
ff = mp.io.lammps.LammpsForcefieldReader().read(Path("system.ff"))
ff = mp.io.gromacs.GromacsTopForcefieldReader().read(Path("forcefield.itp"))
```

AMBER prmtop files contain both structure and parameters.
`mp.io.amber.AmberPrmtopForcefieldReader().read_system` returns both — the force field, and the structure
frame with a `pairs` block for the 1-4 pairs whose `SCEE` / `SCNB` differ from
the field's `special_bonds` (GLYCAM beside ff14SB) — as
`mp.io.gromacs.GromacsTopForcefieldReader().read_system` does for a GROMACS
topology; the inpcrd adds the coordinates:

```python
# docs: skip — reads Amber prmtop/inpcrd artifacts from an offline run
ff, frame = mp.io.amber.AmberPrmtopForcefieldReader().read_system(Path("system.prmtop"))
frame = mp.io.read_inpcrd(Path("system.inpcrd"), frame)
```

### Writing

Each writer produces output in a specific engine format from a `ForceField` object:

```python
# LAMMPS coefficients (selected by the frame's type labels)
mp.io.lammps.LammpsForcefieldWriter(frame, precision=4).write(Path("system.ff"), ff)

# OpenMM XML
mp.io.openmm_xml.OpenmmXmlWriter(precision=6).write(Path("system.xml"), ff)
```

GROMACS keeps cutoffs in the run parameters (`.mdp`), not in the topology, so
the `.itp` writer does not write the pair style's cutoff — the same `ff` feeds
both writers:

```python
mp.io.gromacs.GromacsTopForcefieldWriter(precision=4).write(Path("system.itp"), ff)
```

### Type filtering

LAMMPS force field files should include only the types actually used in the
system. `LammpsForcefieldWriter` does that by construction: the frame's type
labels select the coefficients, so a large library force field writes only what
the system uses. A frame label the force field has no type for raises
`ValueError` naming the block and the label.

### Supported force field formats

| Format | Read | Write | Notes |
|--------|------|-------|-------|
| Force-field XML | `xml.XmlForcefieldReader().read` | `xml.XmlForcefieldWriter().write` | Every style of a force field, in its declared units; a write followed by a read gives the same force field |
| OpenMM XML | `openmm_xml.OpenmmXmlReader().read` | `openmm_xml.OpenmmXmlWriter().write` | OpenMM's own schema (nm, kJ/mol); the writer refuses what OpenMM cannot express; `write_system(path, ff, frame)` adds the residue templates of a frame |
| LAMMPS coefficients | `lammps.LammpsForcefieldReader().read` | `lammps.LammpsForcefieldWriter(frame).write` | Coefficients selected by the frame's type labels |
| LAMMPS data `* Coeffs` | `lammps.LammpsForcefieldReader().read_data_coeffs` | `lammps.LammpsForcefieldWriter(frame).write_data_coeffs` | The reader takes the frame `read_lammps_data` returned; the writer writes the sections alone (to a path, or a `bytearray` for the text), for the caller to splice into a data file |
| GROMACS `.top` / `.itp` | `gromacs.GromacsTopForcefieldReader().read` | `gromacs.GromacsTopForcefieldWriter().write` | Force-field directives |
| GROMACS system | `gromacs.GromacsTopForcefieldReader().read_system` | `gromacs.GromacsTopForcefieldWriter().write_system` | `(ForceField, typed Frame)`, 0-based |
| AMBER prmtop / frcmod | `amber.AmberPrmtopForcefieldReader().read` | `amber.AmberFrcmodWriter().write` | Force-field tables |
| AMBER system | `amber.AmberPrmtopForcefieldReader().read_system` | — | `(ForceField, typed Frame)`, per-pair 1-4 weights in `pairs` |

All of these are in `mp.io`'s format submodules; the `ForceField` they read and write is `mp.ff.forcefield`'s.

## Extending with new formats

A new format is a native reader and writer in the Rust core, published on `mp.io`. The workflow is documented in the **[Developer Guide: I/O Formats](../developer/extending-io.md)**.
